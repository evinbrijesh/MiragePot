### 3. Attacker Profiling System

**Skill Level Estimation** (`miragepot/server.py:_estimate_skill_level()`)
- Analyzes attacker sophistication using multi-factor heuristic:
  - **Command tier distribution** (filesystem vs. cache vs. LLM usage)
  - **TTP detection results** (stages, confidence, technique diversity)
  - **Honeytoken interaction** (credential access indicates targeted behavior)
  - **Session duration and command count**
- Three skill levels:
  - **Script Kiddie**: Random commands, high LLM tier usage, low sophistication
  - **Intermediate**: Mixed tactics, some reconnaissance, knows common paths
  - **Advanced**: Targeted actions, multi-stage attacks, credential exfiltration, low LLM usage

**Tier Usage Tracking** (`miragepot/command_handler.py`)
- Added `tier_usage` dict to session state: `{"filesystem": 0, "cache": 0, "llm": 0}`
- Increments appropriate counter for each command based on handling path:
  - **Filesystem tier**: Built-in commands (`cd`, `ls`, `pwd`, `cat`, etc.) + interactive handlers
  - **Cache tier**: Pre-cached responses for common utilities
  - **LLM tier**: Novel commands requiring AI generation
- Stored in session logs and used for skill level estimation at session end
- Enables understanding of attacker sophistication (advanced attackers use fewer LLM-tier commands)

## Technical Implementation Details (Session 2)

### Command Dispatch Architecture

**Before (O(n) if/elif chain):**
```python
if cmd_name == "cd":
    return _handle_cd(...)
elif cmd_name == "pwd":
    return _handle_pwd(...)
elif cmd_name == "ls":
    return _handle_ls(...)
# ... 20+ more branches
```

**After (O(1) dict lookup):**
```python
_BUILTIN_DISPATCH = {
    "cd": (_handle_cd, 1),
    "pwd": (_handle_pwd, 0),
    "ls": (_handle_ls, 1),
    # ... all commands in dict
}

# Dispatch
handler, offset = dispatch[cmd_name]
return handler(args[offset:], state)
```

**Performance characteristics:**
- Worst-case lookup: O(n) → O(1)
- Memory overhead: ~2KB for dispatch tables
- Lazy initialization prevents import-time overhead

### LLM Cache Implementation

**Cache structure:**
```python
_SESSION_LLM_CACHE: Dict[tuple, str] = {
    ("ls -la", "/root"): "total 48\ndrwxr-xr-x...",
    ("ps aux", "/root"): "USER  PID  %CPU...",
    # ... up to 100 entries
}
```

**Cache key generation:**
- Tuple of (command_string, current_working_directory)
- Directory matters: `ls` in `/root` ≠ `ls` in `/etc`
- Command string includes arguments: `ls -la` ≠ `ls`

**Eviction policy:**
- FIFO (First-In-First-Out) when size > 100
- Simple but effective for session-scoped cache
- No LRU overhead (session lifetime typically short)

**Hit rate expectations:**
- High for reconnaissance patterns (multiple `ls`, `cat`, `ps`)
- Low for unique commands (download attempts, custom scripts)
- Typical session: 30-50% hit rate on 10-20 commands

### Dashboard Caching Strategy

**Cache TTL selection rationale:**
- `load_session_logs()` - 30s: Balance freshness vs. I/O for historical data
- `load_session_tags()` - 60s: Tags change infrequently (manual edits)
- `load_live_sessions()` - 10s: Need near-real-time updates for active sessions

**Cache invalidation:**
- Write operations clear related caches explicitly
- Streamlit's `@st.cache_data` handles TTL expiration
- No cross-request state (stateless per Streamlit design)

## Lessons Learned & Best Practices

### Performance Optimization
1. **Profile before optimizing**: Metrics showed command dispatch was O(n) bottleneck
2. **Measure impact**: Cache hit rates should be monitored in production
3. **Trade-offs**: 2KB memory overhead for O(1) lookup is excellent trade

### Code Organization
1. **Separation of concerns**: Static assets vs. runtime data
2. **Lazy initialization**: Dispatch tables built on first use, not import time
3. **Explicit cache invalidation**: Better than implicit TTL-only strategies

### Testing Philosophy
1. **Test behavior, not implementation**: "Commands work via dispatch" not "Dispatch dict has 20 entries"
2. **Regression prevention**: Tests lock in Phase 2/3/4 improvements
3. **Fast feedback**: 604 tests run in ~2.5 seconds

### Version Management
1. **Semantic versioning**: 0.1.0 → 0.2.0 for minor version bump (new features, no breaking changes)
2. **Changelog hygiene**: Diary serves as detailed changelog for this release
3. **Git discipline**: All changes uncommitted until ready for atomic commit
