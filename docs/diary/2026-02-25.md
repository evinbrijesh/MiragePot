## Phase 1 Fixes — All 8 Implemented

### Fix 1: Hardcoded DEBUG log level (`server.py:44–52`)

**Problem:** `logging.basicConfig(level=logging.DEBUG)` was hardcoded, completely ignoring the `MIRAGEPOT_LOG_LEVEL` environment variable that already existed in `config.py`.

**Fix:** Log level now resolved dynamically at startup:
```python
_log_level_str = get_config().logging.level.upper()
_log_level = getattr(logging, _log_level_str, logging.INFO)
logging.basicConfig(level=_log_level, ...)
```
Defaults to `INFO` in production. Set `MIRAGEPOT_LOG_LEVEL=DEBUG` to re-enable verbose output when needed.

---

### Fix 2: Passwords logged whenever DEBUG was active (`server.py:319`)

**Problem:** The password logging condition was:
```python
if security_config.log_passwords or LOGGER.level <= logging.DEBUG:
```
The `or LOGGER.level <= logging.DEBUG` clause meant passwords were always logged as long as DEBUG was active — which it always was due to Fix 1. This completely bypassed the `MIRAGEPOT_LOG_PASSWORDS=false` safety guard.

**Fix:** Removed the DEBUG bypass entirely. Passwords are now only logged when `log_passwords` is explicitly `true` in config:
```python
if security_config.log_passwords:
```

---

### Fix 3: Hardcoded hostname `"miragepot"` in TTYHandler (`server.py:334`)

**Problem:** The shell prompt always showed `root@miragepot:~#` regardless of the `MIRAGEPOT_HOSTNAME` config setting. An attacker who sees the hostname `miragepot` immediately knows something is off.

**Fix:**
```python
# Before
tty_handler = TTYHandler(session_state=session_state, hostname="miragepot", ...)

# After
tty_handler = TTYHandler(session_state=session_state, hostname=config.honeypot.hostname, ...)
```
Now controlled by `MIRAGEPOT_HOSTNAME` env var. Default remains `"miragepot"` but can be set to anything (e.g., `"ubuntu-prod-01"`).

---

### Fix 4: Hardcoded SSH login banner (`server.py:339`)

**Problem:** The banner sent to every attacker on login was hardcoded as a bytes literal:
```python
chan.send(b"Welcome to Ubuntu 20.04.6 LTS (GNU/Linux 5.15.0-86-generic x86_64)\r\n")
```
Not configurable, and didn't use the `os_name`, `os_version`, and `kernel_version` fields already defined in `HoneypotConfig`.

**Fix:** Banner now assembled from config values:
```python
os_banner = (
    f"Welcome to {config.honeypot.os_name} {config.honeypot.os_version} "
    f"(GNU/Linux {config.honeypot.kernel_version} x86_64)"
)
chan.send((os_banner + "\r\n").encode("utf-8"))
```
Controlled by `MIRAGEPOT_OS_NAME`, `MIRAGEPOT_OS_VERSION`, and `MIRAGEPOT_KERNEL_VERSION`.

---

### Fix 5: `import traceback` inside except blocks (`server.py:249, 266`)

**Problem:** `import traceback` appeared twice inside except blocks — a Python anti-pattern. Imports belong at the top of the file.

**Fix:** Added `import traceback` to the standard library imports at the top of the file and removed both inline imports.

---

### Fix 6: Hardcoded version and Python version in metrics (`metrics.py:188–189`)

**Problem:**
```python
system_info.info({
    "version": "1.0.0",       # pyproject.toml says 0.1.0 — mismatch
    "python_version": "3.11", # wrong for anyone running Python 3.12/3.13
})
```
Two separate version inconsistencies in one block.

**Fix:** Both values now resolved dynamically at runtime:
```python
from importlib.metadata import version as _pkg_version, PackageNotFoundError
import sys

try:
    _version = _pkg_version("miragepot")  # reads from pyproject.toml
except PackageNotFoundError:
    _version = "dev"

system_info.info({
    "version": _version,
    "python_version": f"{sys.version_info.major}.{sys.version_info.minor}",
})
```

---

## Key Decisions

### Why not fix the `TODO: implement cursor movement` in `tty_handler.py`?

The left/right arrow key cursor movement is a known incomplete feature (lines 513, 517). It was intentionally left for a future session because:
- It requires tracking cursor position within the buffer and recalculating terminal output on each character insert/delete
- It's non-trivial and out of scope for a bug-fix pass
- The current behaviour (ignoring left/right arrows) is harmless — the attacker just can't move the cursor inline

This is documented as a known limitation, not a bug.

### Phase 1 scope: surgical fixes only

All 8 fixes were deliberately narrow — no restructuring, no new modules, no refactoring. Each fix touched the minimum number of lines needed to correct the specific problem. This keeps the diff reviewable and the risk of regression low.
