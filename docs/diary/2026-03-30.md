### 2. Architectural Exploration

**Deep dive into MiragePot's internal systems:**

**Logging System** (`server.py`):
- Session logs stored as JSON in `data/logs/session_{hex}.json`
- Complete capture: metadata, SSH fingerprint, auth attempts, PTY info, commands, downloads, TTP summary, honeytokens
- Real-time dashboard updates via `live_sessions.json`
- Automatic log rotation: 30-day retention, 10,000 file cap

**TTP Detection** (`ttp_detector.py`):
- 146 pre-compiled regex patterns matching MITRE ATT&CK techniques
- 10 attack stages: Reconnaissance → Credential Access → Persistence → Privilege Escalation → Defense Evasion → Lateral Movement → Collection → Exfiltration → Impact
- Risk level calculation: Low (basic recon) → Medium (2+ stages) → High (3+ high-confidence indicators) → Critical (5+ indicators or Impact/Exfiltration)
- Multi-command chain detection for advanced techniques

**Honeytoken System** (`honeytokens.py`):
- 7 token types: AWS keys, DB passwords, API keys (Stripe/GitHub/Slack), JWT secrets, SSH private keys
- Embedded in realistic locations: `.aws/credentials`, `.env`, `config.php`, `passwords.txt`, `.gitconfig`
- Exfiltration detection: curl POST, wget, nc, scp, rsync
- Complete tracking: access events + exfiltration attempts with destinations

**Threat Scoring** (`defense_module.py`):
- Keyword-based scoring: 0-150+ scale
- Examples: `ls` (5), `wget` (60), `nc` (70), `rm -rf` (120), fork bomb (150)
- Tarpit delays: <40 (no delay), 40-79 (1-2s), 80-119 (2-4s), ≥120 (3-5s)

**Prometheus Metrics** (`metrics.py`):
- Exposed at `:9090/metrics` endpoint
- Key metrics: `connections_total`, `sessions_active`, `commands_total{threat_level}`, `ttp_detections_total{attack_stage,technique}`, `honeytokens_triggered_total{token_type}`
- Real-time event tracking for all attack activities

**Critical Finding:**
- MiragePot has comprehensive event detection and logging
- **No existing notification/webhook system** - perfect opportunity for enhancement
- Clear integration points identified in `server.py` and `command_handler.py`

### 3. Notification System Design

**User Requirements Gathered:**
- Platforms: Discord webhooks + Telegram Bot API
- Timing: Both real-time alerts AND session-end summaries
- Filtering: High and Critical risk only (reduce noise)
- Honeytokens: Alert on both access and exfiltration attempts
- JSON logs: Include both attachment and inline summary

**Architectural Design:**

**Module Structure:**
- `miragepot/notifications.py` - Core notification module (new)
  - `NotificationManager`: Orchestrates delivery, filtering, rate limiting
  - `DiscordNotifier`: Rich embeds with color-coded risk levels
  - `TelegramNotifier`: Formatted messages with document uploads
  - `NotificationQueue`: Async queue for non-blocking delivery
  - `RateLimiter`: Token bucket algorithm (10 notifications/min default)

**Configuration:**
- New `NotificationConfig` dataclass in `config.py`
- 13 environment variables for complete control
- Integration with existing config system

**Integration Points:**

*Real-time Alerts (immediate):*
1. **High-threat commands** (`server.py:913-920`) - threat_score >= 80
2. **Honeytoken access** (`command_handler.py:2823`) - AWS/SSH keys viewed
3. **Exfiltration attempts** (`command_handler.py:2830`) - curl POST, wget with tokens

*Session-end Summaries (complete analysis):*
- **Location**: `server.py:1013-1032`
- **Trigger**: High/Critical risk sessions on disconnect
- **Content**: Full TTP analysis, attack stages, honeytokens, commands, risk level
- **Attachment**: Complete `session_xxx.json` file for forensics

**Technical Specifications:**

*Discord Integration:*
- Webhook API (no bot registration needed)
- Rich embeds with color coding: Red (Critical), Orange (High), Yellow (Medium), Blue (Low)
- File attachments up to 8MB
- Rate limit: 5 requests per 2 seconds

*Telegram Integration:*
- Bot API with `sendMessage` + `sendDocument`
- Markdown formatting for readability
- File uploads up to 50MB
- Inline keyboard buttons for actions
- Rate limit: 30 messages per second

*Async Architecture:*
- Non-blocking delivery via `asyncio.create_task()`
- Background worker processes queue
- Graceful degradation on failures (log error, continue honeypot)
- <50ms latency impact on attack detection

**Security Considerations:**
- Webhook URLs stored in environment (never committed)
- Command output sanitization to prevent injection
- Discord markdown escaping
- Message size limits (truncate long commands)
- No sensitive internal system details in notifications

**Performance Impact:**
- Latency: <50ms added to attack detection (async queue)
- Memory: ~5MB for notification queue (bounded)
- CPU: Negligible (HTTP calls offloaded to asyncio)
- Network: 1-5 KB per notification, <1 MB with JSON attachment

## Key Insights

### Architecture Quality
MiragePot has exceptional instrumentation:
- **Complete event capture**: Every attack action logged with context
- **Rich threat analysis**: MITRE ATT&CK mapping with 146 patterns
- **Real-time metrics**: Prometheus exposes all events immediately
- **Well-structured code**: Clear separation of concerns, easy to extend

**The missing piece**: External notification system to leverage all this data.

### Notification System Value Proposition
1. **Immediate incident response**: Teams alerted within seconds
2. **Complete forensics**: Full session logs attached for analysis
3. **Reduced noise**: Risk-based filtering (High/Critical only)
4. **Team collaboration**: Discord/Telegram enables coordinated response
5. **Actionable intelligence**: MITRE ATT&CK techniques identified

### Design Decisions

**Why Discord + Telegram?**
- Discord: Popular with security teams, excellent embed support, simple webhooks
- Telegram: Global reach, better mobile experience, 50MB file uploads
- Both: No complex OAuth, straightforward API, rich formatting

**Why async architecture?**
- Honeypot performance cannot be compromised
- Notification failures must not crash SSH sessions
- Bursts of attacks need queuing to respect rate limits
- Background delivery enables retry logic

**Why risk-based filtering?**
- Low/Medium risk sessions create alert fatigue (scanner noise)
- High/Critical sessions indicate real attacks worth investigating
- Configurable threshold allows customization per deployment

**Why both real-time + session-end?**
- Real-time: Enables active response during ongoing attacks
- Session-end: Provides complete context and forensic data
- Together: Best of both worlds without duplication

## Technical Debt & Considerations

### Potential Challenges
1. **Rate Limiting**: Discord 5 req/2s, Telegram 30 msg/s - need careful queue management
2. **File Size Limits**: Discord 8MB, Telegram 50MB - may need JSON compression for long sessions
3. **Network Failures**: Webhook timeouts, API errors - need robust retry logic
4. **Error Handling**: Must not crash honeypot on notification failure
5. **Testing**: Need real Discord/Telegram channels for integration tests

### Design Tradeoffs
1. **Async vs Sync**: Chose async for performance, adds complexity
2. **Push vs Pull**: Chose push (webhooks), more immediate but requires internet access
3. **Rich vs Simple**: Chose rich formatting (embeds), better UX but platform-specific
4. **File Attachment vs Link**: Chose direct attachment, more convenient but size limited

### Future Optimization Opportunities
1. **Batch Notifications**: Group multiple attacks from same IP into single message
2. **Smart Deduplication**: Don't send duplicate alerts for repeated commands
3. **Notification Templates**: Allow users to customize message format
4. **Cloud Upload**: For large JSONs, upload to S3 and include download link
5. **Bi-directional Integration**: Allow responding to attacks via Discord/Telegram commands
