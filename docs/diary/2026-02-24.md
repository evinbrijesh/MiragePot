### Fix 1: `data/system_prompt.txt` + `miragepot/ai_interface.py` — Dynamic Hostname

**Problem:** Lines 11, 34, and 36 hardcoded `miragepot` as the hostname. Since this file is the LLM system prompt read at runtime, it would always tell the AI the hostname is "miragepot" regardless of the `MIRAGEPOT_HOSTNAME` env var.

**Solution:**
- Replaced the 3 hardcoded occurrences with `{hostname}` placeholders
- Updated `_load_system_prompt()` in `ai_interface.py` to substitute `{hostname}` with `get_config().honeypot.hostname` at load time
- The fallback prompt (used when the file is missing) already used `get_config()`, so now both paths are consistent

## Key Technical Decision: System Prompt Hostname

**Options considered:**
- **A:** Generate the entire system prompt in Python code (no text file)
- **B:** Use `{hostname}` placeholders in the text file and substitute at load time

**Chose B** because the system prompt is a long, carefully crafted 94-line document that's much easier to maintain and review as a standalone text file. Simple `.replace("{hostname}", hostname)` in the loader keeps it readable without sacrificing flexibility.

## Lessons Learned

### Documentation Rots Faster Than Code

The architecture doc was written when the project had 8 modules. It now has 19. None of the 11 new modules were documented. The troubleshooting guide had env var names (`OLLAMA_MODEL`) that never existed in the actual config system — likely copied from Ollama's own docs without checking MiragePot's config layer. Regular doc audits after feature work are essential.

### Env Var Naming Consistency Matters

The `OLLAMA_MODEL` vs `MIRAGEPOT_LLM_MODEL` issue is a classic problem: the underlying tool (Ollama) uses one name, but the project wraps it in its own config layer with a different name. Documentation that references the raw tool's env vars instead of the project's own will mislead users.
