## CRITICAL

### BUG-01 — Ed25519/ECDSA Key Generation Crash

**File:** `miragepot/ssh_interface.py`  
**Lines:** 180, 184, 196, 200  
**Status:** Open

**Description:**  
The backend crashes immediately on startup whenever Ed25519 or ECDSA host keys
need to be generated (i.e. on any fresh install or after key deletion).

The P2-07 fix generates Ed25519/ECDSA keys using the `cryptography` library,
wraps them via `paramiko.Ed25519Key.from_private_key()` /
`paramiko.ECDSAKey.from_private_key()`, then tries to persist them with
`.write_private_key_file()`. Paramiko does not implement
`write_private_key_file()` on keys loaded via `from_private_key()` — the call
falls through to the `PKey` base-class stub which raises
`Exception("Not implemented in PKey")`.

RSA keys are unaffected because `RSAKey.generate()` is still available in
Paramiko 4.x and the generated object does implement `write_private_key_file()`.

**Impact:**  
- Container crashes on first boot and enters a restart loop every 30 s.
- Health checks fail; Prometheus scrapes return timeouts.
- No SSH connections possible.

**Fix approach:**  
Replace the generate-then-wrap-then-save pattern with generate-save-load:

1. Generate the raw key using the `cryptography` library.
2. Serialise to OpenSSH PEM with `private_bytes(Encoding.PEM, PrivateFormat.OpenSSH, NoEncryption())`.
3. Write the PEM bytes **directly to disk** via `path.write_bytes()` + `path.chmod(0o600)`.
4. Load back with `paramiko.Ed25519Key.from_private_key_file()` /
   `paramiko.ECDSAKey.from_private_key_file()` and return that object.

Rename `_generate_ed25519_key()` → `_generate_and_save_ed25519_key(path)` and
`_generate_ecdsa_key()` → `_generate_and_save_ecdsa_key(path)` to make the
combined responsibility explicit.

## HIGH

### BUG-02 — Race Condition in Metrics Singleton

**File:** `miragepot/metrics.py`  
**Lines:** 467–478  
**Status:** Open

**Description:**  
`MetricsCollector.get_instance()` uses a double-checked locking pattern, but
the first `if cls._instance is None` check (line 467) is performed without
holding the lock. Two threads can both pass this check simultaneously and both
enter the `with cls._lock` block. The inner check catches most races, but under
certain CPU reordering / cache-coherency conditions on multi-core systems the
inner check can also be bypassed, resulting in two separate
`MetricsCollector` objects being created.

**Impact:**  
- Prometheus metric objects duplicated; increments go to different instances.
- Metrics data becomes fragmented and inconsistent under high connection load.
- Small probability but reproducible via targeted concurrency testing.

**Fix approach:**  
Remove the outer unprotected check and always acquire the lock:

```python
@classmethod
def get_instance(cls) -> 'MetricsCollector':
    with cls._lock:
        if cls._instance is None:
            cls._instance = cls()
    return cls._instance
```

### BUG-03 — Unbounded Credential Storage

**File:** `miragepot/metrics.py`  
**Lines:** 362–367  
**Status:** Open

**Description:**  
`log_credential_attempt()` appends every unique `username:password` pair to
`self._failed_credentials` (a plain Python `set`) without any size cap on the
set itself. The Prometheus gauge is capped at 1,000 for metric purposes, but the
underlying set grows without limit for the lifetime of the process.

An attacker who submits a stream of uniquely-generated credentials (trivial with
a script) can cause unbounded memory growth.

**Impact:**  
- ~64 bytes per entry × 10 M unique credentials ≈ 640 MB memory consumed.
- No credential sanitisation: binary data or multi-MB passwords stored as-is.
- Long-running honeypots accumulate credentials indefinitely.

**Fix approach:**  
- Enforce a hard cap (e.g. 10,000 entries) on the set itself, not just the gauge.
- Truncate `username` and `password` to a reasonable maximum (e.g. 256 chars)
  before storing.
- Optionally add periodic cleanup to shed oldest entries.

### BUG-04 — Find Command Path Matching Bug

**File:** `miragepot/filesystem.py`  
**Lines:** 604–605  
**Status:** Open

**Description:**  
The virtual `find` implementation checks `current_path.startswith(start_path)`
to decide whether a path is inside the search root. This comparison has a
boundary problem: `/home/user` is a string prefix of `/home/username`, so `find
/home/user` would incorrectly descend into `/home/username` and return its
contents.

The `_under()` helper (introduced in P1.1-06) already handles this correctly for
other commands, but `find` does not use it.

**Impact:**  
- `find /home/user` returns files from `/home/username` (false positives).
- Incorrect results reveal honeypot filesystem inconsistencies to an attacker
  probing carefully.

**Fix approach:**  
Replace the raw `startswith` check with the existing `_under()` helper, which
appends a `/` separator before comparing to avoid the prefix-collision problem.

### BUG-05 — UTF-8 Filtering Breaks Internationalization

**File:** `miragepot/tty_handler.py`  
**Lines:** 415–416  
**Status:** Open

**Description:**  
The P5-07 byte-filtering fix drops all bytes with value > 127:

```python
filtered_data = bytes(b for b in data if b < 128)
```

This destroys valid UTF-8 multi-byte sequences. Every byte of a non-ASCII
UTF-8 character has the high bit set, so Chinese, Arabic, Russian, Japanese,
emoji, and any other non-Latin input is silently erased.

**Impact:**  
- International attackers cannot type non-ASCII characters; input is silently
  dropped, making the honeypot unusable for a significant portion of real
  attackers.
- Breaks any tool or payload that sends UTF-8 encoded strings.
- Reduces honeypot realism and can reveal its nature to observant attackers.

**Fix approach:**  
Validate and preserve valid UTF-8 rather than stripping high bytes:

```python
try:
    decoded = data.decode('utf-8', errors='replace')
    filtered_data = decoded.encode('utf-8')
except Exception:
    filtered_data = bytes(b for b in data if b < 128)
```

Control characters that are genuinely dangerous (null bytes, escape sequences
outside of normal terminal use) should be filtered selectively rather than by
byte range.

### BUG-06 — Incomplete Filename Sanitization

**File:** `miragepot/ai_interface.py`  
**Lines:** 149–169  
**Status:** Open

**Description:**  
`_sanitize_filename()` blocks a list of known-dangerous characters but misses
several Unicode categories that can cause problems:

- **Zero-width spaces** (U+200B, U+200C, U+200D): invisible components that
  make two visually identical filenames map to different paths.
- **Right-to-left override** (U+202E): reverses the displayed filename in
  terminals and file managers (e.g. `report<RLO>txt.sh` displays as
  `reporths.txt`).
- **Byte order mark** (U+FEFF): can break file parsers or create
  duplicate-looking entries.

**Impact:**  
- Log entries and dashboard display can show different filenames than what is
  actually stored on disk.
- Analysts reviewing session logs may be confused or misled.
- Not immediately exploitable for code execution given the sandbox architecture,
  but reduces the integrity of audit trails.

**Fix approach:**  
Strip all Unicode format/control characters using `unicodedata.category()`:

```python
import unicodedata
filename = ''.join(
    c for c in filename
    if unicodedata.category(c) not in ('Cf', 'Cc', 'Cs', 'Co')
)
```

Apply this step before the existing character-replacement logic.

### BUG-07 — File Descriptor Double-Close in Atomic Config Write

**File:** `miragepot/server.py`  
**Lines:** 196–211  
**Status:** Open

**Description:**  
`_write_config_atomic()` creates a temporary file descriptor with
`tempfile.mkstemp()`, wraps it in `os.fdopen()`, then after the `with` block
closes the descriptor tries to call `os.fsync(tmp_fd)` and `os.close(tmp_fd)`.
`os.fdopen()` takes **ownership** of the fd and closes it when the context
manager exits, so both subsequent calls operate on an already-closed file
descriptor, raising `OSError: [Errno 9] Bad file descriptor`. The outer
`try/except` swallows this error, meaning:

1. `fsync` is silently skipped — the write is not guaranteed to reach disk.
2. The double-close is silently ignored — but on some runtimes a recycled fd
   number could be closed unexpectedly.

**Impact:**  
- Config writes are not durably flushed to disk despite the intent of the
  atomic-write pattern.
- Data loss possible during a hard crash immediately after a config write.

**Fix approach:**  
Call `f.flush()` + `os.fsync(f.fileno())` **inside** the `with os.fdopen(...)`
block before it closes, and remove the redundant `os.close()` from `finally`:

```python
with os.fdopen(tmp_fd, 'w') as f:
    json.dump(config_data, f, indent=2)
    f.flush()
    os.fsync(f.fileno())
os.replace(tmp_path, file_path)
```

### BUG-08 — Injection Detection False Positives on International Input

**File:** `miragepot/command_handler.py`  
**Lines:** 2363–2383  
**Status:** Open

**Description:**  
The mixed-script detection added for P2-11 flags any command that contains
characters from more than 2 Unicode scripts as suspicious. The threshold is too
low: many fully legitimate commands exceed it.

Examples that are incorrectly blocked:
- `curl https://例.jp/file_résumé.pdf` (Latin + Kanji + accented Latin)
- `git commit -m 'Fix: 修复错误'` (Latin + CJK)
- `echo 'Hello שלום مرحبا'` (Latin + Hebrew + Arabic)

**Impact:**  
- Legitimate commands from international attackers are rejected.
- Attacker receives an error for valid input, which can reveal that filtering
  is in place.
- Reduces honeypot realism.

**Fix approach:**  
- Raise the threshold from > 2 to > 3 scripts, or
- Strip quoted strings and URLs from the command before counting scripts (these
  are the most common legitimate sources of mixed-script content), or
- Switch to detecting specific high-risk script combinations known to be used
  in homograph attacks (Cyrillic + Latin, Greek + Latin) rather than a blanket
  script count.

### BUG-09 — Rate Limiter Cleanup Race Condition

**File:** `miragepot/rate_limiter.py`  
**Lines:** 96–115  
**Status:** Open

**Description:**  
`_cleanup_old_connections()` builds the list of IPs to remove by iterating
`self._connections` **without holding the lock** (lines 102–106), then acquires
the lock and deletes them (lines 110–113). In the window between building the
removal list and acquiring the lock, another thread can add a fresh connection
from one of the IPs on the list. That new entry is then deleted, and the IP
effectively bypasses rate limiting for one request cycle.

The defensive `if ip in self._connections` check on line 112 prevents a
`KeyError` but does not prevent the deletion of a freshly-added valid entry.

**Impact:**  
- Low probability under normal load, but reproducible with a targeted burst.
- An attacker who times requests carefully could bypass rate limiting for a
  single connection.

**Fix approach:**  
Hold the lock for the entire cleanup operation (iterate + delete):

```python
with self._lock:
    cutoff = time.time() - self._window
    to_remove = [ip for ip, ts in self._connections.items()
                 if not any(t > cutoff for t in ts)]
    for ip in to_remove:
        del self._connections[ip]
```

### BUG-10 — Inconsistent Timestamp Parsing

**File:** `dashboard/app.py`  
**Lines:** 170–178  
**Status:** Open

**Description:**  
`parse_timestamp()` uses three bare `except:` clauses that catch all exceptions
including `KeyboardInterrupt` and `SystemExit`. The three fallback formats also
produce datetimes with inconsistent timezone awareness:

- `datetime.fromisoformat()` — preserves timezone if present, naive otherwise.
- `datetime.fromtimestamp()` — uses the local system timezone.
- `datetime.strptime()` — always returns a naive datetime.

Mixing aware and naive datetimes in comparisons raises `TypeError` at runtime.

**Impact:**  
- Silent swallowing of unexpected exceptions can mask unrelated bugs.
- Timezone inconsistency can cause incorrect session ordering in the dashboard
  or a `TypeError` crash when comparing timestamps from different sources.

**Fix approach:**  
- Replace bare `except:` with `except (ValueError, TypeError, OSError):`.
- Normalise all parsed datetimes to UTC-aware by calling
  `.replace(tzinfo=timezone.utc)` when `tzinfo` is `None`.
- Log a warning when all formats fail so the bad value is visible in logs.
